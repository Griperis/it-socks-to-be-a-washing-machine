Moving the game to native Godot

The old game was built almost entirely in code. It is being rebuilt as a fresh Godot project: hand-authored scenes, typed Resources, models you can swap in the editor, and co-op from the first line. This page is the plan for that port, the decisions that are yours, and the research behind them.

How co-op is structured

Each piece of state is one of four kinds, and the kind decides how it travels. This came out of testing Godot's own multiplayer nodes in 4.7.1 and mapping every co-op mechanism of the old game onto them.

Kind of stateExamplesHow it travels
DecidedA Door is open, a Sock is in your Hands, a Pair is shelved, CoinsA field on the thing's own part in the scene. A player asks with a Command; only the Host's answer writes it. One snapshot serves a late joiner and a save.
Continuous, owned by one machineA player's body, a thrown Sock in the air, a ragdollGodot's synchronizer. The owner follows the decided state: whoever holds a thing moves it.
Created during playAvatars, flying bodiesGodot's spawner, started by the Host.
The MessThousands of resting SocksOne bulk system that counts as one part, with its own compact snapshot. No node per Sock.
  • What a Guest sees early is looks only. A Guest's guess never changes shared state. The old game broke this rule once and two players saw different Socks for weeks.
  • A gate at the door. A player on another version of the game is refused before anything is sent.
  • The Host checks every request: its shape, that the thing exists, that the action is one the thing accepts, and how often it comes.

What an entity is

Behaviour

  • The thing's parts with their state fields, visible in the inspector.
  • The rules: what it accepts, what it refuses and why.
  • The same in the zoo and in the house: never a zoo-only copy.

Looks

  • A child scene you can swap: a graybox now, the model later.
  • State plays an AnimationPlayer inside it, forwards and backwards.
  • A short list of node and animation names it must provide, checked at every merge.

The shape we would move to

  • Rules stay as they are. Game rules, saves and the network snapshot keep using plain data, with no nodes. Scenes and Resources feed them the same data the JSON does today.
  • Every prop is a small scene: a script on the root, the model as a plain child. Swapping a model means replacing that child and moving a few markers.
  • Parts become nodes you can see: colliders, hinge pivots, lamp lights, Sock spots, attachment points. No more lookups by name.
  • One Interactable component replaces ten Station classes and a 294-line aiming chain.
  • Numbers live where you tweak them: typed Resources for balance, the inspector for one prop's own numbers.
  • Broken things fail loudly: warning triangles in the editor, a Validate button and a headless test share one check.

What the research found

Netcode

  • Our netcode already suits the move; nothing in it has to change.
  • Godot's own replication nodes cannot carry 10,000 Socks or node-free rules, so they stay unused for doors, drawers and machines.
  • The one new problem: a hand-placed prop needs a stable network id.

Animation, rigging, Blender

  • The Cat, the washer face and the intro are the safest first moves into the editor.
  • Door swings, UI tweens, Sock cloth and the Avatar's bend are better left as code.
  • Blender keeps shapes, rigs, clips, hulls and marker empties; Godot owns behaviour, wiring, lights and numbers.

Authoring and editor wiring

  • Connect in the editor for visuals inside one prop; connect in code for anything touching rules, saves or the network.
  • One house scene, a scene per floor, over a generated shell nobody edits by hand.
  • A prop's room comes from where it stands, as today.

Duplicates and constants

  • Biggest overlap: aiming and using things. Second: the carried devices that hold Socks.
  • About half of ~590 numeric constants are geometry or UI sizes that become scene or Theme properties.
  • One real drift: cloth.max_accel is 40.0 in code and 12.0 in the JSON.

Your question: is 30% realistic, not 9–10%?

Yes, but not from moving to scenes alone. Scenes give about 12%, and most of that moves into scene files instead of disappearing. Unifying the systems that do the same job adds real deletion and reaches about 16%. 30% needs one of two things on top: your yes to a list of cuts, or rebuilding devices, carried items, views and screens on a few shared systems.

Four Fable agents measured this on 19 November: three went through every folder of the 76,300 lines of game code, one worked top-down from the game's concepts. Scenes and unification figures are mostly counted; rewrite figures are judged from the behaviours to keep, give or take 20–30%.

Recommended path

  1. Delete the dormant features first. 2,500–3,100 lines leave about 70 files before anything is ported.
  2. Spike the item system on the Radio and the Sock detector. Pass: from about 1,300 lines to under 450, their tests green with only lookups edited, a third kind added in under 80 lines. Stop if the shared rule needs a branch per kind.
  3. Spike records that save themselves on the vacuums, with the join snapshot unchanged byte for byte.
  4. The plan's foundations and pilots, with Interactable for Stations and Openables.
  5. Roll the item system out kind by kind, the Cat last.
  6. Containers, then the remaining aim kinds, then input out of the views.
  7. The plan's scene phases, on views that are already thin.
  8. Decide on the state store after a spike with a Guest's predicted pick.

Your ask: one feature at a time, tests written separately, starting from the core

Core first works if "core" means the plug-in points before the insides. Five hub files name almost every feature (the boot file names 37 of 40, Game 29, the Rig 24, the Command table 22), so today every feature move edits them and two moves collide. Give each hub one place to plug in first; then prove the new shared systems on small features; then move the core loop one feature at a time.

A Fable agent cut the game into 41 features and measured who names whom (654 links). Needing a feature to exist is not needing it moved first: a step waits only for the shared system it lands on and the hub it registers with. Sizes after the move are the earlier reports' numbers re-added per feature: about 17–18% smaller with every behaviour kept. Risk ratings, the order inside a wave and the parallel groups are judgment.

Tests written separately, one feature at a time

  1. A behaviour test acts only through the game's own doors: a Command, a network line, Game's public actions or a real input. Never a view, a rules part's functions or a zoo button (your rule, Q2056).
  2. It may read state directly, and finds things through two helper files ("find me a thing that...", in glossary words). The helpers keep a rearranged scene green and shield cases from renames during a move.
  3. A separate agent writes the feature's behaviour tests and its "move contract" on main before the move. Each case is seen to fail once by breaking the rule on a scratch copy, then merged green on the old code.
  4. The move ticket is blocked by the contract ticket. A guard fails any branch that edits a behaviour test unless the ticket names the case, the reason and your answer.
  5. Old tests are sorted in the ticket: kept, rewritten (named), deleted (named, with the case that replaces each).
  6. Guests and late joiners: one scripted game per feature, every machine compared after each step, a Guest joined from the snapshot in each state (lying, held, flying, inside something). A stored snapshot is a pin that one command renews, not a gate.
  7. The 59 suites that load the whole game are not rewritten up front. They keep working until each feature moves; loading the feature's scene is the normal case for a new test.
  8. What the tests are for (your answer, 19 November): that the game works, the core loop most. A test may pin a layout, but pins are few, kept apart, and moving furniture does not turn the important tests red. Details on the fourth tab.

The standard interface every class keeps

30 numbered rules in the report, most with a check a script can run. In short:

  1. State you can read. Everything the Host decides on, a save keeps or a late joiner must see is a typed field of a Record. Anyone reads it, tests included.
  2. One way to change it. game.run(Command) is the only entrance. A decide_ function answers and changes nothing; an apply_ function in a System is the only place a field changes. A function asks or changes, never both.
  3. The Host decides. Host-only work is a Host-only Command; no component, view or screen asks "am I the Host".
  4. Signals say what happened. Past tense, ids not objects, sent only after the change. A handler shows or asks; it never changes state.
  5. A component declares, reads, asks and shows. One function (_show) touches its child nodes. State that is only for looks may live on it.
  6. Names and types. One class a file, a suffix by kind, the glossary's words, everything typed, at most two steps of inheritance.
  7. Who may know whom is one table by kind. Generic systems (Items, Holders, Openables) never name a kind of thing.
  8. Ids, saves, numbers. Every placed thing has a fixed id, never a node path. Saving loops over the state tables, so no class writes its own save code. Numbers live in Defs.
  9. No debug or test hooks in game classes.
  10. Tests follow your answer; see below.

One object in both worlds: scene and rules

  1. The scene is the only source of what exists. A component in the editor declares an ability, its settings and a fixed id.
  2. At New Game the scene is read once into plain data; the rules make one Record for each thing. Until the house is scenes, the same data comes from today's JSON, which is what lets the house move last.
  3. The component gets its Record to read, and using it only sends a Command.
  4. The Host decides, every machine applies, and the component animates the change, or snaps to it on a join or a load. The save stays the join snapshot.

Tests: that the game works, the core loop most

Your answer as rules: a test is a rule about behaviour; it finds things by what they are, not where; layout pins are allowed, few, kept apart and renewed with one command. Four checks run after every case: no Sock lost, every machine equal, a joiner equals the Host, a loaded save equals the World.
