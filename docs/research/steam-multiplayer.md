# What must the game's multiplayer code look like so that Steam drops in at M4 without rework, while M0.6 runs on ENet?

Asked for: M0.6 batch 1 (host, join, roster) and the M4 lobby, Q2456-Q2458, 2026-11-22. Engine 4.7.2.

Every claim below is "read, not tried" unless it says "tried on 4.7.2". Steam cannot run in this sandbox, so nothing about Steam itself was tried.

## Answer

- GodotSteam 4.24 (2026-11-08, MIT, Steamworks SDK 1.65) supports Godot 4.7.2. It comes as a GDExtension zip ("Godot 4.4 and up", unpacked into `addons/godotsteam/`, no custom engine) and as module builds of the editor and export templates, which have a 4.7.2 variant. `SteamMultiplayerPeer` is inside GodotSteam itself; the separate MultiplayerPeer repo is retired. It is a normal `MultiplayerPeer`, so RPCs, spawner, synchronizer and `auth_callback` work over it unchanged.
- The seam is two small things: a transport (ENet or Steam builds the peer, with a "how to reach the Host" value that is opaque: `ip:port` or a Steam ID or lobby ID) and an identity (the one player id of Q2458, proven by a transport-specific step at the gate). The Session's RPCs, Commands, the gate and the roster stay as they are.
- Four ENet assumptions will break on Steam. 1) A join address is not an IP. 2) The peer id is not the player's identity: on Steam it is random per connection and the real identity is a Steam ID reached through `get_steam_id_for_peer_id()`. 3) The Steam peer has no `host.get_local_port()`, and "port" is not a concept. 4) Failure cases arrive differently: a connection that never completes and a Host that quits are reported by Steam's lobby and connection states, with no reason text from the peer signals.
- `auth_callback` and `send_auth` are not ENet-specific. Tried on 4.7.2 over a non-ENet `MultiplayerPeerExtension` with peer id 987654321: the gate, `peer_connected` after `complete_auth`, RPCs both ways and `auth_timeout` all behave as over ENet. The Steam auth ticket (`getAuthSessionTicket` on the Guest, `beginAuthSession` on the Host) therefore fits straight into the gate the Session already has: the Guest sends its ticket where it now sends PROTOCOL. This is not tried with the real Steam peer.
- Only Guest-to-Host traffic is needed, so set `server_relay = true` on the Steam peer. Otherwise `connect_to_lobby()` also opens a connection from every Guest to every other Guest. The Steam peer has no host migration; if the Host leaves, the session ends, as it does on ENet today.
- Tests, CI and LAN keep ENet. A Steam run needs the Steam client running and logged in, and one Steam account per instance, so two Steam clients on one machine need two accounts. Development uses app id 480 (Spacewar).

### 2. SteamMultiplayerPeer

- Where it lives: since GodotSteam 4.17 the MultiplayerPeer repo is merged into the main one ("This Guide Is Deprecated. As of GodotSteam 4.17, the MultiplayerPeer repository has been merged into the main GodotSteam repository."). `register_types.cpp` registers `SteamMultiplayerPeer` in the GDExtension build too (`GDREGISTER_CLASS(SteamMultiplayerPeer)`). Sources: https://godotsteam.com/howto/multiplayer_peer/ , https://codeberg.org/godotsteam/godotsteam/raw/branch/godot4/register_types.cpp . read, not tried. The class reference says "Only available in the main GodotSteam branches": the GDExtension is built from the same branch, so this should include it, but no one ran the zip here.
- The separate extension by expressobits (`steam-multiplayer-peer`, MIT, badge 0.2.3) says "I have paused development on this plugin", "No channel support", and uses Steam Sockets. Not a candidate for a new build. Source: https://github.com/expressobits/steam-multiplayer-peer . read, not tried.
- It is a `MultiplayerPeer` subclass, so Godot's high-level multiplayer uses it through `multiplayer.multiplayer_peer = peer`. GodotSteam's own tutorial uses it with `RPC`, `MultiplayerSpawner`, `MultiplayerSynchronizer`, `set_multiplayer_authority(int(name))` (the same pattern as our Avatar) and `peer_disconnected`. Source: https://godotsteam.com/tutorials/multiplayer_peer/ . read, not tried. That SceneMultiplayer is transport-agnostic is tried below.
- Host and client: `create_host(virtual_port)` sets `unique_id = 1` and a listen socket; `create_client(steam_id, virtual_port)` sets `unique_id = generate_unique_id()` and connects to the Host's Steam ID. `host_with_lobby(lobby_id)` and `connect_to_lobby(lobby_id)` wrap these. There is no IP and no port: the address is a Steam ID. Sources: https://godotsteam.com/classes/multiplayer_peer/ , https://codeberg.org/godotsteam/godotsteam/raw/branch/godot4/godotsteam_multiplayer_peer.cpp (lines 500-540). read, not tried.
- Peer ids: a peer picks its own id and sends it in a handshake packet. The code accepts a claim from the Host's Steam ID only if the id is 1, and from anyone else only if the id is 2 or more and unused. This check came in 4.24 (2026-11-07) after a report that anyone in the lobby could claim peer id 1. So before 4.24 a Guest could pose as the Host; 4.24 or later is a must. Sources: https://godotsteam.com/blog/2026/11/08/godotsteam-424-and-multiplayerpeer/ , the `_is_valid_peer_id_claim` function in the .cpp above. read, not tried.
- Mapping: `get_steam_id_for_peer_id(peer_id)` and `get_peer_id_for_steam_id(steam_id)`. The tutorial uses it for auth ("the peer ID will be different from the client's Steam ID and will not work with beginAuthSession()"). A Guest that reconnects gets a new random peer id. Sources: https://godotsteam.com/classes/multiplayer_peer/ , https://godotsteam.com/tutorials/authentication/ . read, not tried.
- Transfer modes: reliable maps to Steam reliable, unreliable to Steam unreliable, and `TRANSFER_MODE_UNRELIABLE_ORDERED` has a code comment "No equivalent" and is sent as reliable. `get_packet_mode()` on receive reports only reliable or unreliable. So "unreliable ordered" costs head-of-line blocking on Steam; the Avatar's synchronizer and anything that relies on it dropping stale data should be checked. Source: the .cpp above (`_get_steam_packet_flags`, `_get_packet_mode`). read, not tried.
- Channels: a Godot channel becomes a Steam "lane" (`m_idxLane`) and lanes are configured per connection from a Project Setting, `get_max_channels()`. The code falls back to channel 0 with a warning when `p_channel >= configured_lanes - 1`, which looks like an off-by-one (the last configured lane can never be used). Sources: https://codeberg.org/godotsteam/godotsteam/raw/branch/godot4/steam_packet_peer.cpp (lines 42, 66, 99-112). read, not tried. Our code uses channel 0 only (no channel argument in `session.gd`), so it is not affected.
- Packet size: `get_max_packet_size()` returns `k_cbMaxSteamNetworkingSocketsMessageSizeSend`, 512 KiB. Valve: "Messages *can* be larger than a single MTU (UDP packet), but there is no retransmission [for unreliable], so if any piece of the message is lost, the entire message will be dropped." A snapshot sent as one reliable RPC fits and is split by Steam. SceneMultiplayer keeps its own `max_sync_packet_size = 1350` (docs property), meaning each synchronizer packet stays near one MTU on any transport. Sources: godotsteam_multiplayer_peer.cpp line 477; https://partner.steamgames.com/doc/api/steamnetworkingtypes ; https://docs.godotengine.org/en/latest/classes/class_scenemultiplayer.html (the page is "latest", not pinned to 4.7). read, not tried. The ENet side was not compared (see "Not found").
- Relay and NAT: the peer creates its listen socket with `CreateListenSocketP2P` and `SymmetricConnect`, and connects with `ConnectP2P`. Valve: "All P2P connections are automatically relayed over the Valve backbone when appropriate" and Steam Datagram Relay "prevents IP addresses from being revealed". So no port forwarding and no IP are shown. Sources: godotsteam_multiplayer_peer.cpp lines 490-500 (`_create_listen_socket`); https://partner.steamgames.com/doc/features/multiplayer/networking ; https://partner.steamgames.com/doc/api/ISteamNetworkingSockets (ConnectP2P). read, not tried.
- Topology: `connect_to_lobby()` "connects to the rest of the members of the lobby, calling add_peer for each", so by default it is a mesh. The tutorial sets `peer.server_relay = true` ("clients do not communicate directly with each other but are routed through the server peer ... Each client only needs a connection to the server"), and says that without it the Host "may only load the game scene when every peer has connected". Source: https://godotsteam.com/tutorials/multiplayer_peer/ . read, not tried.
- Host migration: none in the peer. The tutorial lists "handle edge cases like the host disconnecting and migrating authority to another peer" as the game's own job. In the code, when peer 1 goes, the peer closes (`_disconnect_peer`: "Close if this was the host we lost"). Sources: https://godotsteam.com/tutorials/multiplayer_peer/ , the .cpp above. read, not tried.
- Disconnects: the connection-state callback calls `disconnect_peer(...)` and emits `peer_disconnected`; Steam's end reason is printed only at debug level (`m_eEndReason`) and is not given to the game. Godot's `peer_disconnected(id)` has no reason either. Source: the .cpp above (`network_connection_status_changed`). read, not tried.
- `set_refuse_new_connections` exists and is honoured in the connection callback. read, not tried.

### 3. Lobbies

- Create: `Steam.createLobby(type, max_members)`; Valve: max 250 members. Set it with `setLobbyMemberLimit` (only the owner). Sources: https://partner.steamgames.com/doc/api/ISteamMatchmaking ; https://godotsteam.com/tutorials/lobbies/ . read, not tried.
- Lobby data: `setLobbyData(lobby, key, value)`, owner only; key length is limited to `k_nMaxLobbyKeyLength` and value to `k_cubChatMetadataMax` (the numbers are not in the doc text read). Members have `setLobbyMemberData`. Source: https://partner.steamgames.com/doc/api/ISteamMatchmaking . read, not tried.
- Invite and join: `activateGameOverlayInviteDialog(lobby_id)` opens the friends overlay. A friend who accepts, with the game running, gets a `join_requested(lobby_id, friend_id)` signal. With the game not running, Steam launches it with the command line `+connect_lobby <64-bit lobby ID>`. Valve says the same for `InviteUserToLobby` (`GameLobbyJoinRequested_t`, or the `+connect_lobby` launch parameter). GodotSteam's tutorial reads this from `OS.get_cmdline_args()`. Sources: https://godotsteam.com/tutorials/lobbies/ ; https://partner.steamgames.com/doc/api/ISteamMatchmaking . read, not tried. Note: our own command-line user args use `--` (`OS.get_cmdline_user_args()` in `zoo_net.gd`); `+connect_lobby` is a plain arg, so a main-scene reader must use `get_cmdline_args()`.
- Lobby owner: Valve: "There always one lobby owner - if the current owner leaves, another user in the lobby will become the owner automatically." The lobby owner can therefore change while the game's Host (peer 1) has not. The Host should be the player who created the lobby and the code should not read the lobby owner after start to mean the game's Host. Source: https://partner.steamgames.com/doc/api/ISteamMatchmaking (GetLobbyOwner). read, not tried.
- Typical flow (GodotSteam's tutorial): Host `createLobby` -> in the created callback `create_host(0)`, `server_relay = true`, `multiplayer.multiplayer_peer = peer`. Guest `joinLobby` -> in the joined callback with `CHAT_ROOM_ENTER_RESPONSE_SUCCESS`, `create_client(getLobbyOwner(lobby), 0)`. The Guest never types an address. Sources: https://godotsteam.com/tutorials/multiplayer_peer/ , https://godotsteam.com/tutorials/lobbies/ . read, not tried.
- A full lobby cannot be joined (the join gives an enter-response error), so the "The game is full" text (Q2443, Q2444) would come from the lobby join result on Steam, and from `max_clients` or the Host's refusal on ENet. The enter-response codes were not read here.
- Callbacks need `Steam.run_callbacks()` every frame, in a node that is never paused. Source: https://godotsteam.com/tutorials/initializing/ . read, not tried.

### 4. Identity

- Local Steam ID: `Steam.getSteamID()` after a successful `steamInitEx()`. Source: https://godotsteam.com/tutorials/remove_steam/ (usage). read, not tried.
- The Guest asks Steam for a ticket, `getAuthSessionTicket(identity)`. Valve's parameter says `pIdentityRemote` is "the identity of the remote system that will authenticate the ticket. If it is peer-to-peer then the user steam ID". The ticket arrives in a `get_auth_session_ticket_response` callback. Source: https://partner.steamgames.com/doc/api/ISteamUser . read, not tried.
- The Guest sends the ticket bytes over the network; the Host calls `beginAuthSession(ticket, size, guest_steam_id)`. Valve: "identity is not confirmed until the callback ValidateAuthTicketResponse_t is received and the return value in that callback is checked for success." The Host must take the Steam ID for that call from the transport (`get_steam_id_for_peer_id`), never from the Guest's message. Sources: https://partner.steamgames.com/doc/features/auth ; https://godotsteam.com/tutorials/authentication/ . read, not tried.
- The callback gives the ticket owner's Steam ID, a result (0 is success) and the game owner's Steam ID, which differs from the first under Family Sharing. On leave: Guest `cancelAuthTicket(handle)`, Host `endAuthSession(steam_id)`. Valve: "Session Tickets must only be used once", so each Guest-Host pair needs its own ticket. Sources: same two. read, not tried.
- The newer `GetAuthTicketForWebApi` (named `GetTicketForWebApi` in the call text) is for a game's own web service through `ISteamUserAuth/AuthenticateUserTicket`. Valve: "This API can not be used to create a ticket for use by the BeginAuthSession/ISteamGameServer::BeginAuthSession. Use the GetAuthSessionTicket API instead". A listen-server Host with no web backend needs `getAuthSessionTicket`, not the web one. Source: https://partner.steamgames.com/doc/api/ISteamUser . read, not tried.
- Listen server: Valve says in a peer-to-peer session "each game client should verify the identity of every other game client". With the Host as peer 1 and relay on, a Guest needs to verify only the Host, if it wants to; the tutorial's "authenticate back" step is optional. The Host is itself a Steam user, so it has its own ticket for each Guest to verify. Source: https://partner.steamgames.com/doc/features/auth ; https://godotsteam.com/tutorials/authentication/ . read, not tried. Whether a Guest should verify the Host is a game choice.
- What Steam proves: that the peer on the connection owns that Steam account (the connection itself is already to that Steam ID, since `ConnectP2P` names an identity). The ticket check adds ownership of the app (`ValidateAuthTicketResponse` licence result) and ban state (VAC and others). That is what Q2458 means by "proven by Steam's auth ticket". The connection's remote identity is, per Valve's types header, the Steam ID of the peer; the code reads it through `GetSteamID64(&m_identityRemote)`. read, not tried.

### 7. What the port's code assumes today

Source: the files named. read, not tried (these are our own code).

## The seam

Assumptions an ENet-only design makes that Steam breaks:

1. A join address is `ip[:port]`. On Steam it is a Steam ID or a lobby ID, and the player never types it (an invite, a friend list, or `+connect_lobby` supplies it). Keep the address an opaque string or value handed to the transport; `split_address()` is ENet's part only.
2. A listening port exists (`session.port`, "Hosting on port %d", `host.get_local_port()`). Steam has none. The roster and labels must not print it unless the transport has one.
3. The peer id is the player. On Steam it is a random id per connection (chosen by the peer, checked by the code above), the Steam ID is the identity, and a rejoin gets a new peer id. Q2448 ("a returning player id where they left") and saves are keyed by the player id of Q2458, never by the peer id. The peer id is only "this connection": use it for RPC targets and for the avatar's authority, and keep a map peer id -> player id, filled at the gate.
4. The gate's proof is a version word only. Steam adds a second proof, the auth ticket, at the same gate: the Guest sends a ticket, the Host calls `beginAuthSession` with the Steam ID taken from the transport, and `complete_auth` waits for `validate_auth_ticket_response`. This stays inside `auth_callback` (tried to work over a non-ENet peer). It is asynchronous (a Steam callback), so the gate must not assume the answer comes in the same frame, and `auth_timeout` (default 3 s) must be longer than the ticket round trip or be raised for Steam.
5. Packet size: Steam sends up to 512 KiB per message; the sync packets are capped at 1350 bytes by SceneMultiplayer. A snapshot RPC is safe on both. Do not design on the "1400 byte" or "fits in one ENet packet" idea either way; and "unreliable ordered" is sent reliable on Steam, so a stream that relies on dropping stale packets needs a check in a Steam run.
6. Connection timeouts and failure texts. ENet has its own timeouts; Steam's `TimeoutInitial` and `TimeoutConnected` are connection config values, defaults not found. Q2447 (give up after 10 s with "Could not reach") should be a timer in the Session, not a property of the peer, so it holds for both. `peer_disconnected(id)` and `server_disconnected` carry no reason on either transport; Steam's end reason is not exposed by the GodotSteam peer. Texts such as "The Host ended the session" must come from the game's own messages, not from a transport reason.
7. `max_guests` as `create_server(max_clients)`. On Steam the cap is the lobby's member limit (up to 250) plus `set_refuse_new_connections`; the Session's own cap check (Q2443) should be the single place that counts, so it does not depend on either.
8. The peer's type. `_peer: ENetMultiplayerPeer` must be `MultiplayerPeer`. `close()` calls `_peer.close()`, which exists on `MultiplayerPeer`.
9. Peer-to-peer mesh by default on Steam (see Findings 2). Our traffic is Guest to Host only, so `server_relay = true`, and the Session must not assume a Guest can RPC another Guest (it does not: `_command.rpc_id(1, ...)`).
10. The `--join=` command line and `+connect_lobby <id>` are two ways into the same call. One entry point (`join(target)` where `target` is the transport's own value) serves the command line, the lobby, and tests.

The seam's shape (a sketch for the lead to turn into a ticket, not a design of the game):

- `Transport` (one script, one step of inheritance, per the code-shape rule; `EnetTransport` and `SteamTransport` extend it): `host(options) -> MultiplayerPeer`, `join(target) -> MultiplayerPeer`, `describe_target() -> String` for the label, `player_proof_for(peer: int) -> PackedByteArray` (what a Guest sends at the gate beyond PROTOCOL; ENet gives empty), `verify(peer: int, proof: PackedByteArray) -> Signal or callback` (what the Host checks; ENet accepts at once), and `steam_id_of(peer)` or `identity_of(peer) -> String`. The Session owns the gate and calls the transport for the proof. Everything above the peer (RPCs, Parts, Avatars, Commands) is already transport-neutral.
- `Identity` (the Q2458 field): `local_player_id() -> String or int` (the Steam ID on Steam, the profile's random id otherwise) and, on the Host, a map `peer id -> player id` filled when the gate completes. Saves, the roster, "returning player" and join toasts read the map, never the peer id. The field needs one type for both kinds of id: a Steam ID is a 64-bit unsigned number (an individual account's is about 7.6e16, which fits GDScript's signed 64-bit `int`; this range was not read from Valve, only recalled, so check it), and the random id of Q2224 may be a different length. A decimal String for both avoids the question.
- The test transport is ENet on loopback (as now) and, where a test needs a second transport shape, a `MultiplayerPeerExtension` loopback like the one tried here. It needs no Steam and runs in CI. The Steam transport is not run in CI.

## Open for the designer

1. The Host and the lobby. When the Host leaves, the game ends for everyone (no migration exists in the peer; Steam's lobby owner would move on its own). Options: (a) the session ends with "The Host ended the session" as now; (b) the lobby stays and the players go back to the lobby to start again with a new Host. Which?
2. Who verifies whom. Options: (a) the Host verifies every Guest's ticket and Guests trust the Host; (b) both ways. (a) is less work; (b) stops a fake Host in a lobby invite.
3. A copied profile on LAN. Off Steam the player id stays the long random one (Q2224, Q2449). Options for a LAN or IP join of a Steam build: (a) it is allowed and uses the random id; (b) a Steam build refuses IP joins and only the lobby works. Does a Steam build keep the LAN and IP join at all?
4. The same player on Steam and off Steam. A player who plays by IP with the random id and later joins by Steam has a different player id, so saves are separate (Q2458 as written). Options: (a) accept it; (b) a one-time "link my old profile" step at M4.
5. Test coverage. Options: (a) Steam is checked by hand with the designer's two accounts at M4 only; (b) a tester machine and two accounts are kept for a regular Steam check before each playtest build.
6. A full lobby. On Steam a fifth player cannot enter the lobby at all, so they never see "The game is full (4 players)". Options: (a) the lobby limit is 4 and the text appears from the lobby join result; (b) the lobby holds more and the Session refuses the fifth with the text. Which wording and place?
7. Invite flow. Options at M4: (a) only the friends overlay invite and `+connect_lobby`; (b) also a public lobby list with a name. Which?
