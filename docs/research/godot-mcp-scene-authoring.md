# Can a Godot MCP server let a CLI agent author scenes through the editor, and why do hand-written overrides get dropped?

Asked for: the decision whether agents author scenes through an MCP / the editor's API instead of hand-writing .tscn/.tres, 2026-11-27. Engine 4.7.2 (pinned minor 4.7).

## Answer
- Yes. One server does it today and was tried here: **hi-godot/godot-ai** (MIT, 3.7k stars, last commit 2026-11-23, Godot 4.7+ only). Its plugin runs inside the editor process and saves with `EditorInterface.save_scene()`, so Godot writes the file itself (uid=, `unique_id`, `parent_id_path`, `[editable]`). It runs in a **headless editor with no display** on Linux (`GODOT_AI_ALLOW_HEADLESS=1 godot --headless --path <proj> --editor`), and it instances scenes, sets properties on instanced children and saves. Tried on 4.7.2 in this sandbox (see Findings).
- Other servers that save through the editor: tomyud1/godot-mcp ("Godlink", MIT, 4.4+), NPGameDev/godot-mcp-toolkit (MIT, 4.2+), IvanMurzak/Godot-MCP (Apache-2.0, 4.3-4.7, needs the .NET editor build and the .NET SDK), yurineko73/Godot-MCP-Native (MIT, headless flag, built on 4.6), ee0pdt/Godot-MCP (stale since 2025-03). Coding-Solo/godot-mcp (6.8k stars) is not an editor path: it runs `godot --headless --script` and re-packs a scene it loaded with plain `instantiate()`.
- No official Godot / Godot Foundation MCP was found (godotengine org repos and godot-proposals searched; the only hit, proposals#14090 "LLM tie in", is closed).
- **The real cause of our dropped overrides is probably not the ids.** Tried on 4.7.2: a hand-written scene with an override on a child of an instanced scene keeps it on load, but a save by the engine drops it unless the file has `[editable path="<instance>"]` for each instance on the path. With the `[editable]` lines, wrong `unique_id`, wrong `parent_id_path` and no ids at all all survived a re-save (the engine rewrote the ids from the real nodes). Evidence in this repo: the editor re-save in the working tree dropped `[node name="Label" parent="Looks" index="2"] text = ...` from `game/zoo/gifts/crate_switch.tscn`, a file with no `[editable]` line; 209 .tscn files are modified and e.g. `game/house/house.tscn` goes 191 to 163 `[node` headers, with zero `[editable` lines before or after.
- So there are two fixes, not exclusive: (a) the agent rule "an override or added node below an instance needs `[editable path=\"...\"]` for the instance and every instance above it", checked by a script; (b) author through godot-ai (or another editor-process server), where `node_manage set_editable_children` is an explicit step.

## Findings

Engine behaviour (source and tried):
- 4.5+ stores a per-node `unique_id=N` and, for a node that belongs to an instanced scene, `parent_id_path=PackedInt32Array(...)` (ids of the instance chain from the saved scene's root down to the parent). Writer: `ResourceFormatSaverTextInstance` writes `parent_id_path` only with a `parent=`, writes `unique_id` unless unassigned. Source: godotengine/godot `scene/resources/resource_format_text.cpp` (tag 4.7.2-stable) lines 2014-2056; reader lines 198-216. read, not tried (but the output format is seen in the tried runs below).
- Purpose and design: PR "Add unique Node IDs to support base and instantiated scene refactorings" (reduz, merged 2025-10-06, 4.5): "These IDs act as a fallback to names when saving... USED AS A FALLBACK... It should not break any current existing scene." Source: https://github.com/godotengine/godot/pull/106837.
- How ids are used on load: a node that an instance override names (`TYPE_INSTANTIATED`, no `type=`) is found first by name under its parent; only if that fails is it searched by id (`_find_node_by_id`), with the warning "A node in the scene this one inherits from has been removed or moved, so a recovery process needs to take place. Please re-save"; if both fail: "Node '...' was modified from inside an instance, but it has vanished" and the override is silently skipped. Source: `scene/resources/packed_scene.cpp` (4.7.2-stable) lines 137-150, 285-318, and `_recover_node_path_index` lines 1945-2005 (id_path is used only for recovery of a NodePath that no longer resolves). read, not tried.
- On load a stored id that disagrees with the real node is overwritten (`ids.write[i] = node->get_unique_scene_id()`, packed_scene.cpp ~302-306); on pack an unassigned or clashing id gets a fresh random one (lines 1099-1123). So a wrong hand-written id costs nothing while the name still resolves. Tried (below).
- Why overrides below an instance are dropped on save: `SceneState::_parse_node` skips any node whose owner is an instanced scene that the saved root has not marked editable (`!p_owner->is_editable_instance(p_node->get_owner())`, packed_scene.cpp line 799, and 1142). Editable instances are read from the `[editable path=...]` lines (lines 693-696) and written back for each marked instance (807-813). The node is loaded and works at runtime, then is not written. read, and tried.
- Tried on 4.7.2 (`Godot_v4.7.2-stable_linux.x86_64 --headless --path <proj> --script resave.gd`: load with `instantiate(GEN_EDIT_STATE_MAIN)`, `PackedScene.pack`, `ResourceSaver.save`, which is the editor's save path): base.tscn (Base/Child/Deep), mid.tscn instancing base as `B`, main.tscn instancing mid as `M` with overrides `M/B/Child` (position) and `M/B/Child/Deep`. Five variants: right ids; wrong `unique_id` and `parent_id_path`; no ids; wrong `parent_id_path` only; and right ids with no `[editable]`. All with `[editable path="M"]` + `[editable path="M/B"]` kept both overrides and rewrote the ids to the true ones (`parent_id_path=PackedInt32Array(888, 555)`, `unique_id=222`); the variant without `[editable]` lost both overrides (output was only the `M` instance line), although `get_node("M/B/Child").position` read (50,50) right after load.
- Open engine issues that touch this and are still open: #117605 "Node unique_ids in scenes that inherit GLB change after every reimport", #115971 "Scenes created in 4.5.1 do not export deterministically in 4.6 unless you re-save them", #125597 "New Nodes are being created as changed". Source: https://github.com/godotengine/godot/issues/117605, /115971, /125597. read, not tried.

## Not found, or uncertain
- Whether `scene_open` + `scene_save` on one of our hand-written scenes through godot-ai preserves overrides: it saves what the editor loaded, so overrides below a non-editable instance are already gone at load time into the save path (same as the tried re-save). The fix for existing files is adding `[editable path=...]` (a script can derive them from the `parent=` paths that go through an instance), then one editor re-save. Not tried on the real game project (the main checkout is the designer's; not touched).
- The exact reason some of the ~120 files lost whole nodes (not only properties) was not traced file by file. Missing `[editable]` explains both an override and an added child below an instance (same skip at packed_scene.cpp 799). A sample check of the other kinds (renamed base nodes, scenes loaded after a base changed) would settle it: for each dropped override, test whether its `parent=` path crosses an instance without a matching `[editable]` line.
- tomyud1, the toolkit, IvanMurzak and Native were not run; their instancing/override handling is read only or unread. godot-ai's bridge was driven by my own small HTTP client, not by Claude Code through `godot-ai attach` (stdio); the stdio launch is documented (docs/client-configuration.md) but not tried.
- No source for how long a headless editor takes to start or how it behaves with the game's 4.7 project (autoloads, plugins such as `addons/yard`, `profily`); a try on a worktree copy would settle it.
- 4.7.2 behaviour only; recheck after an engine bump (packed_scene.cpp changes between minors: this area was rewritten in 4.5).

## Open for the designer
- Should agents (a) keep hand-writing scenes under a new rule and a checker ("every override or added node below an instance needs its `[editable path=...]` lines"), (b) author scene edits through godot-ai in a headless editor (adds a Python/uv server and a plugin in `addons/`, a dependency the kit would own, MIT, Godot 4.7+ only), or (c) both: hand-write, then a headless editor pass that re-saves the scene so Godot writes the ids?
- If (b): is a third-party plugin under `addons/godot_ai/` (with an auto-updater that the project would have to disable) acceptable in the game project, or should it live only in the kit's tools folder and be copied into a throwaway project copy per run?
